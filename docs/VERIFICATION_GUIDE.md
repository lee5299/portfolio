# Real-device verification guide

## 짧은 확인 방법

1. **어디로 가나요:** 로컬에서는 `http://localhost:3000`, 운영에서는 제출한 HTTPS 결과물 주소로 이동한다.
2. **세 단계 안에 무엇을 하나요:** `첫 패스키 등록` → 안전하게 보관한 일회용 코드와 패스키 이름 입력 → 기기의 패스키 확인 완료.
3. **무엇이 보이면 통과인가요:** 상태가 `열림`으로 바뀌고 비공개 항목 3개와 패스키 목록이 보인다.
4. **안 될 때는 무엇이 보이나요:** 잠긴 상태가 유지되고 취소·만료·검증 실패 이유를 알리는 메시지가 보인다.

## 준비

- 로컬 JSON 모드는 `npm run build`와 `npm start`, Supabase 통합 모드는 `.env.local`을 준비한 뒤 `npm run start:supabase`를 실행한다.
- 로컬 모드에서는 콘솔 코드, 운영에서는 `npm run setup-code`로 생성해 보관한 `owner-demo`와 `peer-demo` 원문 코드를 사용한다. 코드는 채팅, 문서, 스크린샷 또는 Git에 남기지 않는다.
- 가능하면 첫 패스키는 기기 내장 인증기, 두 번째 패스키는 별도 보안키나 독립된 기기에 등록한다.
- 개발자 도구에서 기록을 저장하기 전에 Cookie와 credential ID를 마스킹한다.

## 필수 시나리오

### A. 공개·비공개 경계

1. 시크릿 창에서 첫 페이지가 인증 없이 열리는지 확인한다.
2. `/api/private-items`를 직접 요청해 `401`을 기록한다.
3. 최초 HTML 응답에서 비공개 항목의 문구가 없음을 검색한다.

### B. 소유자 패스키 두 개

1. `owner-demo`의 첫 패스키를 등록하고 이름·등록 날짜가 보이는지 확인한다.
2. 로그인 상태에서 다른 기기 또는 보안키로 두 번째 패스키를 추가한다.
3. 목록에 두 개가 보이는 화면을 실제 값이 노출되지 않게 촬영한다.

### C. 계정 격리

1. 별도 브라우저 프로필에서 `peer-demo` 패스키를 등록한다.
2. owner 세션으로 `/api/accounts/account-peer-demo/private-items`를 요청해 `403`을 기록한다.
3. peer 세션으로 반대 요청을 보내 같은 `403`을 기록한다.
4. 전후 양쪽 항목 수가 각각 3으로 유지되는지 확인한다.

### D. challenge 재사용

1. 정상 로그인 요청·응답을 개발자 도구에서 복사하되 쿠키와 credential ID를 마스킹한다.
2. 같은 `ceremonyId`와 assertion을 다시 전송한다.
3. `400 CEREMONY_REJECTED`를 기록한다.

### E. 삭제와 복구

1. 두 패스키 중 하나를 삭제한다.
2. 로그아웃한 뒤 남은 패스키로 로그인해 성공을 기록한다.
3. 삭제한 인증기로 로그인을 시도해 실패를 기록한다.
4. 남은 마지막 패스키의 삭제를 요청해 `409 LAST_PASSKEY_BLOCKED`와 목록 개수 1을 기록한다.

## 증거 정제

- Cookie, `Authorization`, 세션 ID, 일회용 등록 코드: `[REDACTED]`
- credential ID와 공개키: 앞뒤 일부만 보이거나 `[MASKED]`
- 실제 기기 이름, 계정 이름과 운영 경로에 개인정보가 있으면 가상 이름으로 교체
- 정제 전 파일은 `evidence/raw/`에만 두고 제출 전에 삭제

## Planner 통합 시 재검증

- 현재 Vercel origin에서 만든 패스키를 최종 Planner origin에서 재사용하지 않는다.
- 최종 origin/RP ID에서 패스키 두 개를 새로 등록한다.
- 공개·비공개 경계, challenge 재사용, 교차 계정 접근, 하나 삭제 후 로그인과 마지막 삭제 차단을 전부 다시 확인한다.
- 전환 완료 뒤 과제용 passkey, session과 ceremony 레코드를 정리한다.
