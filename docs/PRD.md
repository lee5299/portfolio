# Product requirements

## Users and problem

페이지 소유자는 공개 자기소개는 방문자 누구에게나 보여 주면서 개인 메모와 관리 자료는 자신이 등록한 패스키로 인증한 뒤에만 보고 싶다. 방문자는 계정 생성이나 로그인 없이 공개 소개 페이지를 볼 수 있어야 한다. 심사자는 공개 결과물과 소스에 별도 인증 없이 접근하고, 익명화된 증거로 보안 동작을 확인할 수 있어야 한다.

## Product principles

- 공개 소개 콘텐츠의 접근성은 현재와 같이 유지한다.
- 비공개 자료는 서버가 인증과 소유권을 확인한 뒤에만 전송한다.
- 비밀번호를 만들거나 저장하지 않는다.
- 서버에는 WebAuthn 공개키와 검증에 필요한 메타데이터만 저장한다. 개인키는 애플리케이션 서버에 전송하거나 저장하지 않는다.
- 실제 개인정보 대신 명백히 표시된 가상 데이터를 사용한다.

## Functional requirements

### R1. 공개·비공개 영역

- 첫 화면은 인증 없이 열리는 기존 자기소개 페이지여야 한다.
- 비공개 공간은 공개 영역과 화면에서 분명히 구분되어야 한다.
- 비공개 공간에는 서로 식별 가능한 가상 항목이 세 개 이상 있어야 한다.
- 인증되지 않은 HTML, API 응답 및 페이지 소스에 비공개 내용이 포함되면 안 된다.
- 인증되지 않은 비공개 자료 요청은 401 또는 403으로 거절해야 한다.

관련 기준: T08-C10~C18.

### R2. 패스키 등록

- 서버가 등록 요청마다 고유하고 예측하기 어려운 challenge를 생성하고 검증할 때까지 서버 측에 보관해야 한다.
- 등록 결과에서 공개키, credential ID, 사용자 식별자, 서명 카운터 등 검증에 필요한 값만 저장해야 한다.
- 각 패스키에는 사용자가 알아볼 수 있는 이름과 등록 날짜가 있어야 한다.
- 사용자가 등록을 취소하면 안내를 표시하고 자격 증명 정보를 저장하지 않아야 한다.
- 등록 화면과 문서에서 패스키 저장 위치를 기록할 수 있어야 한다.

관련 기준: T08-C19~C26.

### R3. 패스키 로그인과 세션

- 서버가 로그인 시도마다 새로운 challenge를 생성해야 한다.
- 서버는 저장한 공개키, 예상 challenge, RP ID와 origin을 기준으로 응답을 검증해야 한다.
- 성공한 challenge는 즉시 소비 처리하고, 만료되거나 이미 사용된 challenge는 거절해야 한다.
- 성공한 로그인 뒤에는 서버가 관리하는 인증 상태로 사용자를 식별해야 한다.
- 로그아웃하면 기존 인증 상태를 무효화해야 한다.
- UI와 API 어디에도 비밀번호 입력 또는 비밀번호 기반 인증 흐름이 없어야 한다.

관련 기준: T08-C27~C35.

### R4. 계정별 권한 분리

- 익명 시험 계정 두 개에 각각 다른 패스키와 다른 비공개 자료를 등록해야 한다.
- 요청 URL이나 본문에 다른 계정 식별자를 넣더라도 서버는 인증된 계정의 소유권을 기준으로 자료를 조회해야 한다.
- 두 계정 사이의 비공개 자료 교차 접근을 양방향 모두 거절해야 한다.
- 거절된 접근은 상대 계정의 자료를 읽거나 변경하지 않아야 한다.

관련 기준: T08-C36~C41.

### R5. 복구용 패스키 관리

- 한 계정에 이름이 다른 패스키를 최소 두 개 등록할 수 있어야 한다.
- 등록 패스키 목록에서 이름과 등록 날짜를 확인할 수 있어야 한다.
- 하나를 삭제한 뒤 남은 패스키로 로그인할 수 있어야 한다.
- 삭제한 패스키를 사용한 로그인은 거절해야 한다.
- 패스키가 하나만 남으면 삭제를 차단하고 새 패스키를 먼저 등록하도록 안내해야 한다.
- 마지막 패스키 삭제 요청은 `409 Conflict`로 응답하고 기존 패스키를 유지해야 한다.

관련 기준: T08-C42~C46.

### R6. 제출 및 검증 문서

- 공개 결과물 URL과 소스 URL은 HTTPS 주소여야 하며 새 시크릿 창에서 별도 인증 없이 열려야 한다.
- 인증 구현 설명서는 여섯 항목으로 구성하고, 짧은 확인 방법과 AI 사용 내역을 포함해야 한다.
- 성공·실패·재사용·삭제 시나리오의 요청과 응답을 서로 비교할 수 있게 제시해야 한다.
- 요청·응답 기록의 세션, 토큰, 쿠키 등 비밀값은 가려야 한다.
- 아직 방어하지 못한 위험을 최소 하나 구체적으로 밝혀야 한다.

관련 기준: T08-C01~C03, C47~C53.

## Non-functional requirements

- 운영 환경은 HTTPS를 사용하고 개발 시에는 localhost 보안 컨텍스트만 사용한다.
- challenge는 짧은 만료 시간과 일회성 소비 상태를 가져야 한다.
- 비공개 자료의 권한 판단에 클라이언트가 보낸 계정 ID를 신뢰하지 않는다.
- 인증 오류는 계정이나 credential 존재 여부를 과도하게 노출하지 않는 메시지를 사용한다.
- 로그와 제출 증거에 실제 개인정보, 개인키, 세션 쿠키, 토큰 또는 운영 비밀값을 기록하지 않는다.
- 공개키, credential ID, counter, transport 정보와 패스키 이름이 들어 있는 런타임 파일도 Git에 커밋하지 않는다.
- 공개 페이지는 모바일과 데스크톱에서 사용할 수 있고 키보드 접근성을 유지해야 한다.
- 운영 데이터는 Supabase PostgreSQL에 저장하고 브라우저가 Supabase에 직접 접근하지 않게 한다.
- Vercel 서버 함수만 Transaction pooler 연결 문자열을 사용한다. 애플리케이션 연결은 인스턴스당 1개, prepared statement 비활성화, SSL 필수로 구성한다.
- challenge 소비, 최초 등록, 패스키 추가·삭제와 마지막 패스키 검사는 데이터베이스의 원자적 갱신 또는 트랜잭션에서 처리한다.
- 세션 ID와 ceremony ID 원문은 데이터베이스에 저장하지 않고 SHA-256 해시만 저장한다.

## Acceptance criteria

상세 완료 조건, 시험 순서 및 남길 증거는 [ACCEPTANCE_CHECKLIST.md](ACCEPTANCE_CHECKLIST.md)를 단일 기준으로 사용한다. 구현 완료 선언 전에는 해당 문서의 모든 항목에 상태와 증거 위치를 기록하고 `scripts/validate-project.ps1` 및 구성된 테스트를 실행한다.
